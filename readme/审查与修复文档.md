## 二、高危问题与修复方案

### H-1 证据包"可校验"自证失败 ⭐ 核心卖点受损

**现象（实测）**：`POST /api/tasks/{tid}/evidence` 返回
```json
{"verification": {"all_ok": false, "checks": [
  {"path": "report.json", "ok": true},
  {"path": "model.step", "ok": false},
  {"path": "model.stl",  "ok": false}]}}
```

**根因**：`build_evidence` 只把 extra files 的 **basename + SHA-256** 写进 manifest，从不把文件**复制**进证据目录（`evidence.py:50-57`）；而 `verify_evidence`（`evidence.py:80-84`）按"证据目录/文件名"重算哈希。模型产物实际在 `outputs/<tid>/`，证据目录在 `outputs/evidence/<tid>/`，必然校验失败。附带隐患：多个 extra file 同名时 basename 冲突会互相覆盖。

**修复**（`evidence.py`）：
```python
import shutil

for path in extra_files or []:
    if os.path.exists(path):
        # 落地进证据目录，使 verify 可按此路径重算哈希
        name = os.path.basename(path)
        dest = os.path.join(task_dir, name)
        if os.path.abspath(path) != os.path.abspath(dest):
            shutil.copy2(path, dest)
        files.append({
            "path": name,                       # 相对证据目录的路径
            "sha256": _sha256(dest),
            "bytes": os.path.getsize(dest),
            "role": "模型产物",
        })
```
说明：复制前以 basename 为准，step/stl/summary.json 等当前不会撞名；若未来有同名来源（不同子目录同名文件），可加 `task_id` 或序号前缀。

**验收**：
1. 缺陷板全流程后调 `/evidence`，`all_ok == true`，checks 全 ok。
2. 删除产物后 `report.json` 条目仍为 true（其余按存在性自然 false）。

### H-2 孔数 < 4 的图纸导致 4 个端点 500

**现象（实测）**：2 孔 spec 调 `geometry_summary` → `KeyError`。影响 `/model`、`/report`、`/export`、`/evidence`。

**根因**：`cad.py` 硬编码 `range(1, 5)` 强取 `hole.x1~x4`、`hole.d`；而 `drawing.py:331-337` 只对**实际检测到的孔**生成 `hole.x{i}/hole.y{i}` 参数，真实图纸孔数常为 2~3。`audit/fix` 对缺失参数有跳过防御，`cad.py` 没有。

**修复**（`cad.py`）：`geometry_summary` 与 `build_plate` 改为遍历实际存在的孔：
```python
def _hole_ids(spec: Spec) -> list[int]:
    ids = []
    for i in itertools.count(1):
        if f"hole.x{i}" in spec.params and f"hole.y{i}" in spec.params:
            ids.append(i)
        else:
            break
    return ids
```
- `geometry_summary`：`holes` 列表改由 `_hole_ids` 生成，`hole.d` 用 `spec.params.get("hole.d")` 参与判定（缺失时跳过孔径项并保留其余摘要）。
- `build_plate`：孔环改成 `for i in _hole_ids(spec)`。
- `plate.L/W/T` 仍为必需（解析路径始终生成），可在 `api.py` 端点处统一包一层 422（见 H-4 的端点 catch）。

**验收**：进程内构造 2/3/4/5 孔 spec，`geometry_summary` 返回正确 `hole_count`；live 上对 2 孔图调用 `/model`、`/export` 返回 200。

### H-3 前端 WebGL 资源泄漏（3D 视图随机空白）

**根因**（`ViewerPanel.js`）：
1. effect deps 含 `[geometry, highlight, autoRotate, wire, dims]`：即使只切换"线框"开关，也会 `new THREE.WebGLRenderer` 新建一套 WebGL context + 全部资源；cleanup 只 `controls.dispose()/renderer.dispose()`，**所有 BufferGeometry/Material/CanvasTexture 从不 dispose，也不 `forceContextLoss()`**。
2. 浏览器活动 context 上限约 8~16，超限后旧 context 被强制丢弃 → 画布空白、图例失效，只能刷新。
3. 附带体验缺陷：切换开关/点"定位"会重建场景，相机视角被复位。

**修复**（与视角复位一起改，二选一，推荐 A）：
- **方案 A（推荐）**：一次初始化 + 增量更新。
  - effect `[]`：创建 renderer/scene/controls/camera，注册 resize；cleanup 做全量释放（遍历 dispose + `forceContextLoss()`）。
  - effect `[geometry]`：重建模型 group（dispose 旧 group 的资源再挂新）。
  - effect `[highlight]` / `[wire]` / `[dims]` / `[autoRotate]`：只改材质 flags、`lines.visible`、`controls.autoRotate`，不动场景结构。
- **方案 B（最小改动）**：cleanup 补全释放：
```js
return () => {
  controls.dispose();
  scene.traverse((o) => {
    o.geometry?.dispose();
    const mats = Array.isArray(o.material) ? o.material : (o.material ? [o.material] : []);
    mats.forEach((m) => { m.map?.dispose(); m.dispose(); });
  });
  renderer.dispose();
  renderer.forceContextLoss();
};
```

**验收**：切换线框/尺寸/自动旋转/定位 ×2 轮次后表单无报错，画布持续渲染；控制台无 `THREE.WebGL: context lost`。

### H-4 异常输入 → 裸 500（实测：.txt 上传、mode:"b2"）

**根因**：
1. `POST /api/tasks/from-drawing`（`api.py:127-141`）直接调 `parse_drawing`，其底层可抛 `RuntimeError`（缺 PyMuPDF/OpenCV 依赖）、`fitz` 自身异常（损坏 PDF）、`ValueError`（未检测到外轮廓/无法推断尺寸）——全是**合法用户输入会命中的可预期失败**，无捕获 → 500。
2. `FixReq.mode` 声明为 `str`（`api.py:41-44`），`AutoMode(req.mode)`（`api.py:177`）非法值抛 `ValueError` → 500。

**修复**：
1. `from-drawing` 端点：
   ```python
   try:
       return _create_task_from_drawing_file(dest, ...)
   except (RuntimeError, ValueError, OSError) as e:
       raise HTTPException(status_code=422, detail=f"图纸解析失败：{e}")
   ```
   同步顺带校验扩展名 ∈ `{.pdf,.png,.jpg,.jpeg,.bmp}`（非法直接 422）。
2. `FixReq.mode: AutoMode = AutoMode.A1`、`budget: int = Field(default=None, gt=0)`，让 pydantic 校验非法值返回 422；`CreateTaskReq.preference` 同理改为受限校验（详见后文建议值域检查）。

**验收**：上传 .txt → 422 + 中文可读 detail；`mode:"b2"` → 422（不再 500）；前端 toast 能显示 detail 文案。

## 三、中危问题与修复方案（后端）

### M-B1 SQLite 持久化只写不读（重启后任务失效）

**根因**：`api.py` 全部端点只查内存 `_TASKS`；`save_task` 是唯一 DB 调用，`store.load_task` 生产代码零调用。内存为空时 `GET /api/tasks` 落入 DB 分支把任务列出来，点进去却 404——恢复语义断裂。此外两支返回键名不一致：内存 `{task_id,state}`（`api.py:147`）vs DB `{id,state,updated_at}`（`store.py:67`）。

**修复**：
1. 启动时回灌：`store.load_task` 已返回含 `spec` 的 payload，在 `api.py` 模块导入处或在 FastAPI `startup` 事件里遍历 DB 灌回 `_TASKS`（spec 用 from_dict 重建，或按 store.py 现有约定反序列化）。
2. 键名统一为 `task_id`（`store.py` 内 map 一下）。
3. 兼容：若 spec 反序列化成本高，退路是 DB 只存"只读档案"，`GET /api/tasks` 在内存为空时返回 410 提示"服务已重启"——但推荐做成真恢复。

### M-B2 回归验证基线永不更新

**根因**：`state.py:39` 的 `baseline_ids` 固化为初始 audit 失败集，后续轮次不刷新。修复 A 解决约束 C 后，C 仍在 baseline；若后续修复 B 的参数变化使 C 再次失败，`regression_check` 返回 `after - baseline_ids` 为空 → B 被判"无回归"。当前 demo 蓝图因 `propose_fix` 只改自有参数而未触发，随时可能被触碰。

**修复**（`fix.py:79-82`）：每轮重算当前失败集后再算回归差：
```python
cur = {c.id for c, issue in check_all(...) ...}   # 修复前实况
after = {c.id for ...}                            # 修复后实况
regressions = after - cur_before_this_round
```
或至少在成功落定一轮修复后 `baseline_ids.discard(该约束)`。

### M-B3 override 三重不一致

**根因**（`parse.py:139-156`，实测 `plate.L` 90→120 后 `half.L` 仍 45）：
1. pending 残留旧 param id —— 低置信旧字段把整体档位卡死在 A2；
2. `fields` 出现同一 pid 的两条记录；
3. 依赖 override 参数的 derived 参数从不重算（`parse_blueprint` 不调 `recompute_derived`）。

**修复**：
```python
# override 分支：先 purge 再写
pending = [x for x in pending if x != pid]
fields = [f for f in fields if f.param_id != pid]
```
函数收尾在 return 前统一调用 `propagate.recompute_derived(spec)`。

### M-B4 apply_fix 无事务性

**根因**（`fix.py:66-69`，实测复现）：`set_param` 先写 `p.value` 再触发 `recompute_derived`；若某 derived 的 `expr` 引用未在 `depends_on` 声明的参数（手写蓝图常见），`_eval_expr` 抛 `ValueError`。此时前序 change 已生效、后面 pending，spec 半污染；异常沿 `state.py:72` 上抛后任务状态卡 `VERIFYING`，`used` 已 +1 但 fix 未入 `task.fixes`，后续 /fix 的 before 快照失真。

**修复**：`apply_fix` 开头 `snapshot = spec.clone()`，全程 try/except：
```python
try:
    for change in fix.changes:
        set_param(spec, change.param, change.new, evidence=...)
except Exception:
    spec.params.clear(); spec.params.update(snapshot.params)
    fix.note = f"apply 失败：{type(e).__name__}"
    fix.rolled_back = True
    return fix  # 不抛出
```
`state.py` 主循环亦应 try/except 兜底吞下未预期异常并记 `pending_confirmation`，避免任务状态卡死。

### M-B5 竖版图纸比例尺算反

**根因**（`drawing.py:280-308`）：`ints = sorted({v>=10}, reverse=True)` 强取最大两个为 L/W，且 `scale = rect.w / L` 固定假设长度方向水平。竖版图纸 scale 被低估 W/L 倍，导致 `expected_r`、孔坐标 `x_mm=(cx-x0)/scale`、`y_mm=(y1-cy)/scale`、边距 `per_min` 全部偏移。此外"取最大两个标注"会把孔中心距/间距标注劫持为板长/宽。

**修复**：
- 基础修复：根据 `rect.w/rect.h` 与 L/W 的比例关系匹配，选 `scale = rect.w / L` 或 `rect.h / L`（并相应交换 x/y 映射）。
- 护栏：若 `|rect.w/rect.h − L/W|` 超过阈值（如 0.3），不自动推断整体尺寸，降置信 + 转 pending（人工确认），不要强行出尺寸。

### M-B6 hole_inside 忽略孔半径

**根因**（`rules.py:82-86`）：`m = c.target if c.target is not None else 0.0`，随后 `margins < m - tol` 判负。target 缺省时"孔必须完全位于板内"的语义代化为"孔心在板内"（孔心恰在板边 margin=0 也通过）。

**修复**：有效 margin 门槛取 `max(target or 0, hole_d/2)`；孔径从 spec 取（`c.features` → feature 的 `hole.d` 参数），找不到时按现有 target 逻辑最低保护（行为不变）。

### M-B7 评估指标空转

**根因**（`evaluate.py`）：
1. `budget_ok`（`evaluate.py:39`，`used <= total`）按构造恒真（`state.py:51-53` 在 `used >= budget` 时直接 continue），`budget_compliance_rate` 永远 1.0。
2. `repair_success_rate`（`evaluate.py:37`）在 `attempted == 0` 时给 1.0，零尝试用例（低置信拒绝族、spacing 拒绝族）全部"修复成功"拉高均值。
3. `regression_error_rate`（`evaluate.py:32-33`）把"目标问题未解决"的回滚也算进回归错误，与"修复无效"语义混淆。

**修复**：
- `budget_ok` 改为：不出现 `pending_confirmation.reason == "budget_exhausted"` 且 `resolved > 0`；
- `attempted == 0` 的用例在聚合时跳过（不记 Y/N），并在 aggregate 输出中显式报告"被跳过的用例数"；
- `regression_error_rate` 按 `fix.note/rolled_back` 区分"因为新版本引入回归"与"因为未解决"两类原因。

### M-B8 async 端点在事件循环里干重活

**根因**（`api.py:128,137`）：`from-drawing` 是 `async def`，`await file.read()` 落盘后接着在同一线程跑 `parse_drawing` —— 位图路径会走 OCR + `subprocess.run(..., timeout=30)`（`drawing.py:131-147`），期间**整个事件循环被阻塞**，`/api/health` 等一切请求无响应。

**修复**：`async def create_task_from_drawing` → `def create_task_from_drawing`（FastAPI 自动投线程池）；或读文件保留 async，处理用 `run_in_executor`。一行改动即可，推荐前者。

### M-B9 上传同名覆盖 + 无大小限制

**根因**（`api.py:135-138`）：`dest = uploads/<basename>` 无 uuid 前缀；`await file.read()` 无上限全量进内存。

**修复**：`dest = f"uploads/{uuid.uuid4().hex[:8]}_{os.path.basename(name)}"`；用 `file.size`（若提供）或 content-length 限 ≤ 32MB。`_create_task_from_drawing_file` 内仍用 `os.path.basename(path)` 做展示名。

### M-B10 task_id 撞车静默覆写

**根因**（`api.py:78-80,107`）：`_TASKS[tid] = ...` 不查重。重复 task_id 直接覆盖旧任务且无提示；自动 ID `f"T-{len(_TASKS)+1:03d}"` 并发下可重复。

**修复**：撞车 `raise HTTPException(409, detail=f"任务已存在: {tid}")`；自动 ID 改为 `uuid` 后缀或 `max(_TASKS 键)`：`f"T-{max(int(k[2:]) for k in _TASKS if k.startswith(\"T-\"), default=0)+1:03d}"`。

### M-B11 路径耦合 CWD

**根因**：`api.py:26-29` 的 `_DB/_UPLOADS/_OUTPUTS`、`store.py:11` 均相对路径；从仓库根启动落在根、从 backend 目录启动落在 backend —— 前端难以为证文件定位。**修复**：改为以 `os.path.dirname(os.path.abspath(__file__))`（`app/`）的父目录为基准的绝对路径。

### M-B12 llm.py f-string 语法需 Python ≥3.12

**根因**（`llm.py:74-77`）：`f"...{f'{c['param']} {c['old']}→{c['new']}'...}..."` 的同引号嵌套写法是 PEP 701（3.12+）才合法；3.10/3.11 上 **import 即失败，整个服务起不来**，与 `scripts/setup.py:8` 宣称的 `MIN = (3, 10)` 直接矛盾。当前 3.13 环境侥幸掩盖。

**修复**：内层การ引号改成双引号：`f"{c[\"param\"]}"`（外层用单引号），或先拼 strings 再 join。必须在 3.10/3.11 上加一次导入冒烟测试。

## 四、中危问题与修复方案（前端）

### M-F1 快捷键绕过 busy 防重

**根因**（`app.js:55,61,64` + `store.js:72-74`）：按钮有 `disabled=${s.busy === "fix"}`，但 `Ctrl+Shift+Enter` 直接 `s.runFix()`，`runFix` 无 busy 守卫 → 双击并发两次 POST /fix，后端同一任务 `_TASKS[tid]` 的 `before_values/before_issues/before` 快照与结果被交错覆盖。

**修复**：`runFix` 开头 `if (!task || busy === "fix") return;`（并补 deps）；三个快捷键分支在调用前检查 `busy`；必要时 useRef 存最新 busy 做防闭包过期。

### M-F2 解析请求竞态

**根因**（`store.js:35-70`）：`applyTask/setTask/setGeometry` 无序号/AbortController。两次解析在途时后完成的旧请求会覆盖新任务 → task 来自 B、geometry 来自 A。

**修复**：`useRef` 存递增请求序号，`applyTask` 末尾比对序号，过期丢弃；或对上次 fetch 做 AbortController。

### M-F3 "冲突孔红色脉冲"从不生效（ID 域不匹配）

**根因**（`store.js:38-40` vs `ViewerPanel.js:97-115`）：`applyTask` 塞 highlight 的是 `constraint_id`（`c_h1_inside`），viewer 匹配的是 `hole_h1`（几何孔 id）——不相等，图例声称的脉冲高亮从未亮过。IssueList"定位"反而做了正则换算所以正常。

**修复**：把换算提为共享工具（或复用 IssueList 同一函数）：
```js
const holeFlagFrom = (id) => id?.replace(/^c_h(\d+)_inside$/, "hole_h$1");
applyTask: setHoleFlags(issues.map((i) => holeFlagFrom(i.constraint_id)).filter(Boolean));
```

### M-F4 预算输入未取整/未钳制

**根因**（`app.js:97-98`）：`Number(e.target.value) || 1` 直接塞进 `CreateTaskReq.budget: int`（pydantic 拒绝 3.5）→ 422。

**修复**：`setBudget(Math.min(10, Math.max(1, Math.round(Number(e.target.value) || 1))))`；后端同步加 `Field(ge=1, le=10)`。

### M-F5 resize 使用陈旧高度

**根因**（`ViewerPanel.js:183-188`）：`onResize` 里 `renderer.setSize(w2, h)`、`camera.aspect = w2 / h` 用的都是 effect 首次捕获的 `h`，而 viewer 高度是 `clamp(320px, 42vh, 480px)`，窗口缩放时实际高度会变。

**修复**：`const h2 = el.clientHeight || h;` 并使用 `h2`；可加 `ResizeObserver` 观察容器。
